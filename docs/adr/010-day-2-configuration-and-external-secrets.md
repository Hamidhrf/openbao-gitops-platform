# ADR-010: Day-2 configuration and External Secrets

Status: accepted (2026-09-24)

## Context

OpenBao runs in HA with the PostgreSQL backend and unseals itself (ADR-008, ADR-009). Its `initialize` stanza runs once, at first initialization, and is skipped on every later start, including after a restore from a backup. Anything that has to change after that needs a second mechanism.

The first things such a mechanism has to create are the KV mount, the policies and the Kubernetes auth roles that External Secrets Operator (ESO) needs in order to sync secrets in both directions. That is why the configuration mechanism and the ESO design are one decision.

What I measured in the ESO spike, on a throwaway cluster with ESO 2.11.0 and OpenBao 2.6.2:

- Push works only through ESO's Vault provider. The dedicated OpenBao provider is read-only.
- A store that names a dedicated ServiceAccount and requests audience `openbao` logs in. The same ServiceAccount name in another namespace, a token without that audience, and a read-only role used for writing are all refused.
- A referent ClusterSecretStore logs in with the ServiceAccount of each ExternalSecret's own namespace. A policy templated on the caller's namespace confines each namespace to its own path.
- A referent ClusterSecretStore reports Ready even when the role behind it does not exist. Only the ExternalSecrets show the error.
- A Secret mounted as files is updated in place without a restart. Environment variables are not.
- `updatePolicy: Replace` refuses to overwrite a secret that does not carry ESO's `managed-by` marker. `deletionPolicy: Delete` adds a finalizer, and without the `delete` capability the PushSecret stays in Terminating.

Version check on 24 September 2026:

- ESO v2.11.0, released 18 September 2026, is the current release, and chart `external-secrets-2.11.0` is in the chart index. The project supports only the current minor version.
- The support matrix pairs ESO 2.11 with Kubernetes 1.36, which is the cluster version.
- The provider feature matrix still lists the OpenBao provider as alpha with no push support, so the spike result stands at the version I am pinning.
- ExternalSecret, SecretStore and ClusterSecretStore are `external-secrets.io/v1`. PushSecret is `external-secrets.io/v1alpha1`.
- ESO's Flux guide documents a race in which the validating webhook is registered as soon as the HelmRelease is applied, before its pod serves, so custom resources applied in that window fail. The documented fix is a Kustomization for the custom resources that depends on the operator's Kustomization with `wait: true`.

## Options

Configuration mechanism:

- A Flux-managed Kubernetes Job that logs in through Kubernetes auth and applies the desired state idempotently. No new image and no new controller, because the Job runs the same OpenBao image as the servers.
- A configuration operator such as vault-config-operator or bank-vaults. Custom resources and continuous reconciliation, but written for HashiCorp Vault, unverified against OpenBao 2.6.3, and another controller to pin, run and defend.
- OpenTofu or Terraform with the Vault provider. Needs a state backend and runs outside the cluster, so Git stops being the only source of truth.
- Commands run by hand. Fails the GitOps requirement of the task.

How a change re-runs the Job, given that a Job's spec is immutable:

- The script lives in a ConfigMap generated by kustomize with a name hash. A changed script changes the ConfigMap name, which changes the Job's pod template, which cannot be patched, so Flux replaces the Job. Flux supports this either with `.spec.force` on the Kustomization or with the `kustomize.toolkit.fluxcd.io/force: enabled` annotation on a single resource, and names Jobs as the use case for the annotation.
- A Job name carrying a version that I bump by hand. Explicit, but forgetting it fails silently.
- A CronJob. It also corrects drift made outside Git, at the price of slower feedback and a run every interval whether or not anything changed.

Identity for the Job:

- The existing `openbao-admin` ServiceAccount, which ADR-008 created and whose login is already proven.
- A separate identity with a narrower policy. Its policy and role can only be created by an administrator, so the first run would still be the admin identity. A two-phase bootstrap for little gain.

ESO provider: the Vault provider for both directions, the dedicated OpenBao provider (read-only, so push would be impossible), or the OpenBao provider for pull and the Vault provider for push.

Store objects: two cluster-scoped stores using referent authentication, or a SecretStore in every consuming namespace. A namespaced store cannot reference the CA Secret in another namespace, so the second option means inlining the CA in Git or copying it into each namespace.

Path layout: one KV v2 mount with a prefix per direction, or one mount per direction, and what to call the mount, given that the admin policy from first initialization covers a fixed set of paths and cannot be rewritten by the stanza that created it.

## Decision

Configuration mechanism:

- A Kubernetes Job in the `openbao` namespace, applied by Flux, running the image pinned in ADR-009. It reads its script from a ConfigMap generated by kustomize with a name hash, so a change to the script is what triggers a new run.
- The Job carries `kustomize.toolkit.fluxcd.io/force: enabled` so Flux replaces it when its pod template changes. The Kustomization itself keeps `force: false`, because the same directory also holds the two stores, which should not be replaced that way.
- No `ttlSecondsAfterFinished`. A Job deleted by Kubernetes would be missing from the cluster and recreated by Flux on the next reconcile, which would run it again for no reason.
- `restartPolicy: Never` and `backoffLimit: 3`, so each attempt is its own pod and the logs of failed attempts survive. The script waits for OpenBao to answer before it does anything, so a slow start does not consume the attempts.
- A Job that has exhausted its attempts is re-run either by a change to the script in Git or by deleting the Job, after which Flux applies it again on the next reconcile. There is no state to clean up first, because every step is idempotent.
- The Job authenticates as the `openbao-admin` ServiceAccount from ADR-008, with a projected token at audience `openbao`, and talks to the `openbao-active` Service so writes reach the active node.
- It owns the KV mount, the ESO policies and the ESO Kubernetes auth roles. It does not touch the seal, the admin policy or the admin role, which belong to first initialization.
- It discovers the Kubernetes auth mount accessor at run time and renders the templated policies with it, rather than carrying an accessor from today's database in Git.
- It prints what it changed, never a secret value.

ESO:

- ESO comes from chart `external-secrets` version 2.11.0, pinned exactly, in its own namespace, as part of the controllers layer. The chart's images are not overridden. I pin by digest only the images I choose myself, such as the PostgreSQL image in the Cluster and the OpenBao image of ADR-009. Images inside a chart follow the chart's pinned version.
- The custom resources are applied by a later Kustomization that depends on the controllers with `wait: true`, which is the documented answer to the webhook race.
- `rbac.serviceAccountTokenCreate` is disabled, and each consuming namespace gets a Role that lets ESO create tokens only for the two ServiceAccounts named there.
- The Vault provider is used in both directions.

Secrets layout and access:

- One KV version 2 mount at `secret`, with `secret/apps/<namespace>/...` for secrets that OpenBao holds for workloads and `secret/pushed/<namespace>/...` for secrets that workloads send to OpenBao. The name is `secret` because the admin policy that the `initialize` stanza wrote once already grants `secret/*`, and that stanza cannot run again. Any other mount name would mean either extending the admin policy from the Job, which crosses the boundary this ADR draws between first initialization and day two, or adding a second administrative identity for no gain. OpenBao 2.x mounts no KV engine by default, so nothing occupies that path. No path is ever both the source of a pull and the destination of a push, which is what makes a sync loop impossible by construction. Version 2 is required because ESO marks the secrets it manages with custom metadata.
- Two cluster-scoped stores, `openbao-pull` and `openbao-push`, both using referent authentication, so each one logs in with a ServiceAccount resolved in the namespace of the resource that uses it. Both carry `spec.conditions` with an explicit namespace list, so ESO refuses the store to any other namespace before OpenBao is contacted at all.
- Each consuming namespace has ServiceAccounts `eso-pull` and `eso-push`, both with `automountServiceAccountToken: false`.
- The two Kubernetes auth roles bind those names, an explicit list of namespaces and the audience `openbao`, set `token_no_default_policy`, and issue tokens with a TTL of 20 minutes and a maximum of one hour.
- The two policies are templated on the calling namespace. Pull grants read under `secret/data/apps/<caller>/`. Push grants create, update and read under `secret/data/pushed/<caller>/` and its metadata path, and delete only there. A role bound more widely than intended still cannot reach another namespace's path.
- Both stores read the CA from the `ca.crt` key of the listener Secret in the `openbao` namespace through `caProvider`, so the CA is neither committed nor copied.
- ExternalSecrets refresh every hour by default. The demo uses one minute so that propagation is visible in the evidence.
- PushSecrets use `updatePolicy: Replace`, so a secret in OpenBao that ESO did not create is never overwritten. `deletionPolicy: Delete` is used only under the demo prefix, where deleting the PushSecret is meant to remove the remote secret.

Repository layout, extending ADR-006: ESO goes under `infrastructure/controllers/`, and a new Flux Kustomization `openbao-config` reconciles `platform/openbao-config/` between `openbao` and `apps`, holding the script, the Job and the two stores. The ServiceAccounts and the token Role of a consuming namespace live with that namespace under `apps/`.

### Amendment to ADR-008

ADR-008 says the admin role is bound to a ServiceAccount that no application runs as. The day-2 Job runs as it. The Job is the platform's own configuration step rather than an application, it runs in the `openbao` namespace, and its token is short-lived and audience-bound, but the sentence in ADR-008 is now too absolute and is corrected here.

## Limitations

- The Job runs when its script changes, not continuously. Configuration changed by hand inside OpenBao stays changed until the next run. A production platform would run the same idempotent reconciliation periodically or use a configuration controller with its own custom resources.
- Because the policies are rendered with an accessor discovered at run time, Git holds a template rather than the literal policy. A comparison between Git and the live configuration cannot be a text diff.
- The Job holds an administrator identity. A larger platform would give the reconciler its own identity and a narrower policy. Here that would need a bootstrap step that only an administrator could perform, so it buys nothing.
- ESO's controller reads Secrets across the cluster by design, and Kubernetes RBAC cannot grant access to a single key inside a Secret. Reading the CA through `caProvider` therefore removes duplication and a rotation chore, but it is not a privilege boundary: the controller that reads `ca.crt` can read the private key in the same Secret. The boundary that does hold is that neither store's namespace holds the seal key and the certificate authority's own key at the same time.
- Creating a PushSecret is a privileged action. Anyone who can create one in an allowed namespace can have ESO read a Secret from that namespace and write it into OpenBao. PushSecrets stay under Flux, and permission to create them is not given to application users.
- `deletionPolicy: Delete` couples the two lifecycles: deleting the PushSecret removes the data in OpenBao. That is why it is limited to the demo prefix. Where OpenBao is the system of record, the default of keeping the remote secret is the right one.
- A referent cluster-scoped store reports Ready before any consumer has used it, so its status is not evidence that a namespace can authenticate. Only a working ExternalSecret or PushSecret is.
- Referent authentication and the store conditions are behaviour of ESO 2.11. Both are re-tested when ESO is upgraded.
