# Evidence

Command output saved while building and testing this platform. Each file begins with the UTC time it
was captured. These are records, not live runs.

This is a selection. The full set of captures is larger and is kept outside the repository. Every file
here proves one thing the platform claims, and the last column says where that claim is explained.

No secret value appears in any of these files. OpenBao's audit log replaces every value with an HMAC,
so audit lines show which path was touched and by which identity, never what was stored.

The numbers follow the order of the platform, not the order in which the work was done.

| File | What it shows | Explained in |
|---|---|---|
| `01-cluster-nodes.txt` | Four nodes at v1.36.4, one control plane and three workers, the control-plane taint, and where every pod is scheduled | ADR-001, README |
| `02-flux-state.txt` | The Git source, every Flux Kustomization Ready at the same revision, and the HelmReleases | ADR-003, ADR-006, README |
| `03-postgres-cluster.txt` | Three PostgreSQL instances, one per worker, all conditions true, the first scheduled backup completed, and the recovery window | ADR-004, README |
| `04-postgres-quorum-blocked.txt` | Two of three workers stopped. The operator refuses to promote and logs `Strong consistency check failed. Preventing failover.` Writes stop rather than risk losing acknowledged commits | ADR-004, README |
| `05-backups-and-wal.txt` | Backups after two days of running: WAL archiving, the scheduled base backups, and the recovery window from 23 to 25 September | ADR-005, docs/backup-restore.md |
| `06-restore-and-pitr.txt` | A full restore and a point-in-time restore, side by side with the running cluster. The row counts differ, and the timeline history file records where recovery stopped | docs/backup-restore.md |
| `07-openbao-deploy.txt` | Three OpenBao replicas, one per worker, on the PostgreSQL backend. The storage parameters read back from the startup log, the static seal with no recovery shares, one cluster ID, and the two tables OpenBao created in PostgreSQL | ADR-008, ADR-009, README |
| `08-eso-pull.txt` | OpenBao to Kubernetes. A value written by an administrator reaches the workload's mounted file, and the pod keeps its original start time with zero restarts | ADR-010, README |
| `09-eso-push.txt` | Kubernetes to OpenBao. A certificate generated by cert-manager is pushed into OpenBao, carrying the `managed-by: external-secrets` marker that the operator-written path does not have | ADR-010, README |
| `10-eso-isolation.txt` | Three refusals: a token without the `openbao` audience, a write across the pull and push prefixes, and a read of another namespace's path that no policy mentions | ADR-010 |
| `11-tls-external.txt` | The API answering over TLS through the host port, with the platform CA, and two negative controls: without the CA, and by IP address | ADR-007, ADR-011, README |
| `12-dr-recovery-verified.txt` | After the cluster was deleted and rebuilt: the marker row survived, archiving resumed on a new catalogue generation, and all three generations are listed | docs/disaster-recovery.md |
| `13-dr-openbao-identity.txt` | The same OpenBao came back: same cluster ID, same KV mount, same Kubernetes auth accessor, and a pulled secret with its original timestamps | docs/disaster-recovery.md |

Two files are worth reading together. `12` and `13` are the answer to what a recovery actually returns:
data comes back from the database with its original timestamps, while credentials the platform
generates are made again by the controller that owns them.
